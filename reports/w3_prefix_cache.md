# W3 视觉前缀缓存分析 —— 原理 + 收益边界（诚实定位）

> 日期：2026-08-25 · 模型 Qwen2.5-VL-3B · 定位：W3「引擎/推理层优化」的第 4 项

---

## 一、什么是视觉前缀缓存

VLM 的推理分三段，视觉部分是「前缀」：

```
图片 ──► vision tower（32 层 ViT）──► visual tokens ──► projector ──► LLM（36 层）
        (a) 视觉编码，输出 hidden   (b) 映射到文本空间    (c) 文本+视觉 token 一起进 LLM
```

「视觉前缀缓存」= 当**同一张图**被多次请求时，把 (a)(b) 的产物（视觉 token 的
hidden states，或更细的 LLM KV cache）**只算一次、缓存复用**，省去重复计算。

两种粒度：

| 粒度 | 缓存什么 | 省掉什么 | 实现难度 |
|---|---|---|---|
| 粗（vision tower 输出） | 视觉 token 的 hidden states | vision tower 前向（32 层 ViT） | 中（HF 可拆） |
| 细（LLM KV cache 前缀） | 视觉 token 对应的 K/V | LLM 对视觉 token 的 attention | 高（HF `generate()` 不暴露） |

---

## 二、为什么理论上能省（定量收益上界）

收益取决于两件事：**视觉编码耗时占比 P**，和**前缀重复率 R**。

```
收益 ≈ P × (1 − 1/重复次数) ≈ P × R（R=重复请求占比）
```

- 视觉编码耗时占比 P：见 `w3_profile.md` 实测（W3-2 profiling 已产出）：
  小票视觉 token 373、P ≈ **9.7%**；大扫描件视觉 token 2622、P ≈ **16.2%**。
  与粗判方向一致：视觉 token 越多、P 越高，视觉编码（ViT 前向）在大图上抬升；
  但绝对值低于粗判——视觉编码比预期的便宜，瓶颈仍在文本自回归。
- 前缀重复率 R：**这是本项目场景的决定性变量**（见下）。

**结论先行**：前缀缓存能省的，最多是「视觉编码」这部分，且**只在同一视觉前缀被
重复请求时才成立**。它省不掉文本生成（每次 query 的生成部分都是新的）。

---

## 三、本项目的收益边界（诚实，关键判断）

本项目 `/extract` 接口是**一次性抽取**：一张票据图 → 4 个字段 JSON，**每张图只
请求一次**。这意味着：

- 视觉前缀重复率 R ≈ 0 → **收益 ≈ 0**。
- 前缀缓存的真实收益场景是「同图多 query」：多轮对话（同一张图连问「总价多少？
  日期呢？公司名呢？」）、同图分批问不同字段、或「先 OCR 整张图、再按需抽字段」。

**这不是实现失败，而是「优化要匹配场景」的判断**：对一次性抽取，视觉前缀缓存是
「用不上的优化」；强行实现（还牺牲了 `generate()` 的简洁）是负收益的过度工程。
这个判断力本身，比「我实现了视觉前缀缓存」在讲解里更值钱——体现你懂得**先算
收益再动手，而不是追着方法名跑**。

---

## 四、为什么 HF 原生下难做干净（工具链约束的延伸）

1. HF 的 `model.generate()` 在**内部管理 KV cache**，不暴露「跨请求复用同一段
   视觉 KV」的接口。要做细粒度前缀缓存，必须手动拆「vision tower → projector →
   LLM」三段，绕过 `generate()` 自己拼 KV cache 和 attention mask，工程量大、
   极易引入 padding/position 错误。
2. 这正是 vLLM 的 **prefix caching** 内置能力解决的问题——但 vLLM 在原生 Windows +
   Blackwell sm_120 上装不了（W2 已实证）。所以「能做前缀缓存的引擎装不了、
   装得了的引擎（HF）原生不支持」——又是一个「模型新、卡新、系统小众」的工具链
   真空区实证。

---

## 五、结论与讲解口径

- **视觉前缀缓存是「多轮/同图」场景的优化，不是「一次性抽取」场景的**。
- 本项目诚实做法：讲清原理 + 定量收益上界 + 明确「一次性抽取场景收益≈0」的边界，
  **不硬造一个假实现**（延续第一个项目「Kappa 不造假」的诚实原则）。
- 可讲解：「我评估过视觉前缀缓存，算出它在我的 `/extract` 一次性抽取场景收益
  趋近于零，所以没做——但我知道它该用在多轮同图场景，也知道 vLLM 的 prefix
  caching 是怎么做的。优化要匹配场景，不是追着方法名跑。」

## 附：若要扩展（后续真实收益场景）

- 场景扩展：`/ask` 多轮接口（同一张图连续多问），此时前缀缓存从「负收益」变
  「正收益」，再回来实现细粒度 KV 复用。
- 粗粒度版本（vision tower 输出缓存）在 HF 下相对可控：把 `processor` + vision
  tower 的前向拆出来，同一图片 hash 命中则跳过重算——这是「有真实场景就值得做」
  的后续项，本阶段不硬做。
