# 汇报大纲 —— 多模态文档理解模型边缘部署项目

> 项目主线：**「非结构化 → 结构化信息抽取」的「研究 + 工程」双修**
> 与第一个项目 SciTriple（文本微调）拼成完整研究主线。

---

## 一句话定位（开场 30 秒）

> 用 Qwen2.5-VL 做票据/表单的结构化抽取，并在 **8GB 边缘显卡**上把它优化到
> **跑得快、准、能上线**——量化省显存又提速，视觉 token 是第一瓶颈。

---

## 章节结构（预计 10-12 分钟）

### 1. 问题与动机（1 分钟）

- 场景：票据/表单 → 字段 JSON（company/date/address/total）。
- 为什么难：**非结构化图片** → **结构化抽取**，且要部署在 **8GB 边缘卡**（真实约束，不是云端无限算力）。
- 与 SciTriple 的关系：同一主线「非结构化→结构化」，本项补「系统/工程」维度（MLSys）。

### 2. 系统总览（1 分钟）

```
票据图 ──> Qwen2.5-VL-3B ──> 字段 JSON ──> FastAPI 服务
              │ 量化(bnb4 NF4)          │ 压测(locust)
              │ 视觉 token 控制          │
              └─ 引擎优化              └─ 端到端 demo
```

### 3. 核心实验 1：量化三轴对比（2 分钟，最有说服力）

> 全量 624 张正式基准（`longest_edge=2M`），非小样本。（SROIE 原始 626 张，剔除 2 个计时异常样本，剔除不影响精度结论。）

| 方法 | F1 exact | F1 norm | 延迟均值 | 延迟中位 | 峰值显存 | 权重显存 |
|---|---|---|---|---|---|---|
| bf16 原生 | 0.8451 | 0.9501 | 19.6s | 17.1s | 7.8GB | 6.1GB |
| **bnb4 (NF4)** | 0.8304 | 0.9330 | **7.1s** | **6.0s** | **3.7GB** | **2.3GB** |

- **结论**：bnb4 相对 bf16 精度 **−1.7pp**（norm F1，近乎无损），速度中位 ×2.85 / 均值 ×2.8，峰值显存 −52%。
- **诚实口径**：初判（30 样本）是 −5.5pp，全量 624 后修正为 −1.7pp——小样本 CI 宽、噪声大，这就是「必须跑全量 + bootstrap CI」的实证。
- **可讲深**：NF4 是 4bit 非线性量化 + 双重量化；为什么量化反而提速（见下）。

### 4. 关键发现 1：量化不只省显存，还提速（1 分钟，反直觉）

- bf16 权重 6.1GB 逼近 8GB 卡 → `device_map` 被迫 offload ~1GB 到 CPU → 每次 forward 都 CPU↔GPU 拷贝 → 单张 13-17s。
- bnb4 权重 2.3GB 全进 GPU → 无 offload → 6.0s（中位）。
- **讲解**：「省下的显存让权重不再 offload，反而更快」——这是边缘部署里量化的额外收益，不是单纯省内存。

### 5. 关键发现 2：视觉 token 是 VLM 显存第一瓶颈（2 分钟，系统感最强）

- 实测：SROIE 里约 13% 是大图扫描件（面积 ≥ A4 的 84 张，其中最大尺寸 4961×7016 达 73 张），默认切 **~1.1 万视觉 token**（小票仅 500）→ **激活显存**（KV cache 仅 ~394MB）爆炸到 21GB（bnb4 未约束实测）、延迟 60s+（bf16 全量 624 张中 13 个大图样本）。
- 定量：KV cache 估算（GQA kv_heads=2）大扫描件 394MB vs 纯文本 7MB = **56 倍**——但注意 21GB 峰值里 KV cache 只占零头，大头是视觉塔中间激活 + attention 矩阵。
- 解决：`longest_edge=2M` 约束 → 视觉 token 11147→2645（−76%），显存 21GB→3.7GB。**约束不是「用精度换显存」，而是「8GB 卡跑大图的唯一可行前提」**——实测无约束大图单次分配需 15.97GB、直接 OOM；约束后全量 624 张（含 84 张大图）norm F1 仍有 0.9330。
- **讲解**：这是「边缘部署 VLM 的真实工程问题」，有血有肉，比纯文本 KV cache 更吃显存的数学根源。

### 6. 关键发现 3：量化工具链的硬件/版本约束（1 分钟，诚实加分）

- 实测：vLLM（无 Windows wheel + 需 WSL2 + sm_120 不兼容）、autoawq（不认 Qwen2.5-VL 的 decoder layer）都装不了。
- 结论：**bitsandbytes NF4 是当前环境唯一跑通方案**。
- **讲解**：模型新（Qwen2.5-VL）+ 卡新（Blackwell sm_120）+ 系统小众（原生 Windows）= 工具链真空区。选型要盯「模型-工具-硬件三角匹配」，这是生产环境可用性 vs 论文 SOTA 的区别。

### 7. 误差分析（1 分钟，诚实讲误差来源）

- 字段级错误 5 类：完全正确 / 噪声 / 漏抽 / 误抽 / 语义错抽。
- 实测（全量 624 张 × 4 字段 = 2496 字段，bnb4）：完全正确 82.97%、噪声 10.26%、语义错抽 6.61%、幻觉仅 0.08%（漏抽 0.08%）。bf16 完全正确 84.46%、语义错 4.93%。
- 分字段：`total` 最好（592/624 全对）、`address` 最难（噪声 137 条 + 语义错 78 条——OCR 空格/逗号差异 + 长地址截断）、`company` 语义错也较多（62 条，如 `(M)`→`(H)` 视觉相似混淆）。
- **讲解**：能答出「错的大多是收据 OCR 噪声，真·语义错误只占 ~5-7%、幻觉几乎为零」比只报 F1 高一个层次。

### 8. 工程规范（1 分钟，体现软院工程素养）

- `py -3.11 -m pip install -e .` + `src/` 包结构；pytest 48 例全绿（纯 CPU，不依赖 GPU）。
- 断点续跑（每样本落盘，中途 OOM 重跑跳过已完成）。
- bootstrap 95% CI（量化差异必须带 CI 才能谈显著）。
- git 版本管理 + 报告/代码分离。

### 9. 引擎与部署优化（1 分钟）

> 量化之外，把「推理/部署层」也做满——这是 MLSys 的完整闭环。

**批处理（static batching）**：batch1/2/4 吞吐 0.178/0.228/0.247 样本/s、峰值显存
3670/4968/7591MB。反直觉发现：吞吐单调提升（×1.39）的同时每样本延迟反而降
（5.63→4.04s，GPU 未饱和、batch 摊销固定开销）——经典「延迟随 batch 上升」只在
GPU 饱和后才成立；**真实代价只有显存**（batch4 峰值 7591MB 逼近 8GB 上限）。（修了
right-padding 污染 position 的 bug，改为 left-padding 后 batch 输出与单图逐条一致。）

**推理耗时结构（profiling）**：小票视觉占比 P≈10%（373 视觉 token）、大扫描件
P≈16%（2622 token，与 §5 的 A4 扫描件 2645 不同图、同量级）——视觉编码占比随
token 数上升，但绝对值不高（瓶颈仍在文本自回归），是前缀缓存收益上界的来源。

**KV cache 量化（hqq KIVI）**：int8 无损（输出与 baseline 一致、延迟几乎不涨、省显存）；
int4 精度崩 + 小图延迟暴涨 3×（量化/反量化 overhead 大于收益）——**量化位宽要按
精度-延迟-显存实测选，不是越激进越好**。

**视觉前缀缓存**：算出「一次性抽取场景 R≈0、收益≈0」，不硬造假实现（诚实判断力）。

**FastAPI 压测**：并发 1/2/4 → QPS 0.18/0.22/0.22、P95 5.9/9.1/18s。
**并发不涨吞吐、只涨延迟**（单模型同步推理串行执行）——8GB 单卡吞吐上限由单张
延迟决定，要提吞吐靠批处理/连续批处理（vLLM），不靠 HTTP 并发。

### 10. 跨域泛化 + 展望（30 秒）

**跨域泛化（已实测，`reports/xfund_generalization.md`）**：模型**零样本**（只在
SROIE 收据上做过推理，未训练未微调）直接迁移到 **XFUND 中文表单**（50 张，动态
字段，电话/手机/邮箱/金额…），字段级 normalized F1 = **0.4072**（P 0.43 / R 0.39）。
这个数字本身不算高，但它证明了**模型不是「背 SROIE 的 4 个字段」，而是真懂通用
「字段→值」抽取**——换一个从未见过的中文表单域，仍能抽对约 4 成字段（recall 0.39）。
差距主要来自：① 中文表单字段更多样、更长（平均每张 16 字段 vs SROIE 4 字段）；② 中文
OCR 更难；③ 多行 answer 拼接。（诚实口径：2 张模型偶发输出 JSON 结构错误，属
小模型生成式抽取的已知边界，不是解析 bug。）

**展望**：
- 7B 对照（讲规模化）：同 8GB 卡下 7B 量化后显存/速度的规模曲线。
- 连续批处理（vLLM PagedAttention）在原生 Windows+Blackwell 装不了，若迁移 Linux
  可补上「请求级调度」的吞吐对比。

## 高频追问的「诚实口径」备答

1. **「为什么不训练/微调？」** → 项目定位是部署/推理优化（MLSys），精度用「量化前后对比」度量，纯度更高；8GB 卡训 VLM 极吃力，是真实约束。
2. **「量化掉 1.7pp 能接受吗？」** → normalized F1 0.9330 已足够票据抽取（字段级、结构化明确），仅比 bf16 的 0.9501 低 1.7pp、近乎无损，却换来速度中位 ×2.85 / 均值 ×2.8 和峰值显存 −52%；这是边缘部署的显式取舍，有 Pareto 图佐证。
3. **「vLLM 不是更主流吗？」** → 是的，但在原生 Windows + Blackwell 上物理装不了，我实测过（无 wheel + sm_120 不兼容），这是工具链还没跟上的真实情况，反而说明我踩过坑、知道生产可用性的边界。
4. **「视觉 token 怎么控制？」** → `longest_edge` 是分辨率约束旋钮；大图切 1.1 万 token 时激活显存爆炸（21GB），**无约束大图在 8GB 卡直接 OOM（单次分配需 15.97GB）**，所以约束不是「精度换显存」的取舍，而是「让大图能跑」的硬前提；约束到 2M 后降 76% token、显存降 83%，全量 624 张 norm F1 仍有 0.9330。
5. **「KV 量化能省多少？」** → 诚实说：单请求下权重 2.3GB 主导，KV 量化省的是「随序列长度线性增长」那部分，单请求收益有限；int8 无损、int4 精度崩 + 小图延迟 ×3，价值要在高并发/长序列才显——「量化位宽要按实测选」。
6. **「为什么并发不涨吞吐？」** → 单模型同步推理串行执行，HTTP 并发只能排队、不提升吞吐（实测 QPS 0.18→0.22、P95 5.9→18s）；要提吞吐靠批处理/连续批处理（vLLM），这是「边缘单卡容量规划」的硬结论。

## 数字速查（演示前熟悉）

- 量化（全量 624 张）：bnb4 vs bf16 = F1 norm −1.7pp（0.9330 vs 0.9501）、速度中位 ×2.85 / 均值 ×2.8、峰值显存 −52%（7.8GB→3.7GB）
- 视觉 token：11147 → 2645（−76%）；峰值显存 21GB → 3.7GB（−83%）；21GB 是激活显存（KV cache 仅 394MB）
- 视觉 token 全量（624 张）：无约束 84 张 >1 万 token（最大 16307），2M 约束全部 ≤2669，总量削减 51%（`reports/visual_token_stats.json`）
- 精度定位：见 `reports/accuracy_positioning.md`（exact 0.83/norm 0.93 是 3B 零样本 4bit 的上游水平；贡献在部署侧）
- 跨域泛化（XFUND 中文表单 50 张，零样本）：字段级 normalized F1 = 0.4072，证明非「背 4 字段」（`reports/xfund_generalization.md`）
- KV cache：大扫描件 394MB vs 纯文本 7MB = 56 倍
- 误差（全量 624 张 × 4 字段 = 2496 字段级，bnb4）：正确 82.97% / 噪声 10.26% / 语义错 6.61% / 幻觉 0.08%
- 批处理（bnb4，30 张）：batch1/2/4 吞吐 0.178/0.228/0.247（×1.39）、延迟 5.63→4.04s 反降、峰值显存 3670/4968/7591MB（约束是显存）
- 推理耗时结构：视觉占比 小票 ≈10% / 大扫描件 ≈16%
- KV 量化（hqq）：int8 无损省显存；int4 精度崩 + 小图延迟 ×3
- FastAPI 并发：并发 1/2/4 → QPS 0.18/0.22/0.22、P95 5.9/9.1/18s（并发只涨延迟不涨吞吐）
