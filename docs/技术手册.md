## 0. 先用三句话定位这个项目

1. **做了什么**：从 SROIE 收据图片中抽取 company / date / address / total 四个字段，封装成 HTTP 服务。
2. **怎么做的**：Qwen2.5-VL-3B-Instruct **零样本** + bnb4 NF4 量化 + 视觉 token 约束 + FastAPI 服务化。
3. **结果是什么**：624 张全量，normalized F1 0.9330、exact F1 0.8304；中位延迟 6.0s，峰值显存 3710MB，单卡 QPS 0.22。

**一句话价值**：
> 我没有再训一个模型，而是回答“一个 3B 多模态模型能不能在 8GB 边缘设备上跑得动、跑得快、扛得住并发”；用同一批图、同一 prompt、同一台机器，测出精度-延迟-显存的 Pareto 曲线。

## 3. VLM 架构与视觉 token

### 3.1 Qwen2.5-VL 三段式

```text
图像 → ViT（视觉编码器）→ patch 序列 → projector → 视觉 token
文本 → tokenizer → 文本 token
两者拼接 → LLM（自回归生成）
```

- ViT 把图切成 patch（14×14，2×2 merge → 每个视觉 token 对应 28×28 像素）；
- 动态分辨率：图越大，patch 越多，视觉 token 越多；
- projector 把视觉特征映射到 LLM 的 embedding 空间。

### 3.2 视觉 token 估算

$$\text{tokens}\approx \frac{H\times W}{28\times 28}$$

例如 2000×2000 → 约 5102 token；16307 token 对应约 1280 万像素（含动态切块）。

### 3.3 为什么视觉 token 是瓶颈

- 视觉 token 进 LLM 后，每层 attention 的 K/V 都要存；
- KV cache 随 token 数线性增长；
- 84 张图 >1 万 token，最大 16307，KV 推到 21GB；
- 无约束时峰值 15.97GB，直接 OOM。

### 3.4 2M 像素约束

`longest_edge = 2,097,152` 像素：

- 单图视觉 token 上限约 **2669**；
- 总视觉 token 削减 **51%**；
- KV cache 从 **21GB → 3.7GB**；
- 8GB 卡可跑。

**权衡**：降分辨率会损失小字/密集表格；本项目选择“能跑优先”，normalized F1 0.9330 证明代价可接受。

**讲解要点**：
> “这不是模型显存不够，是 token 数没约束。把视觉 token 从最大 16307 压到 2669，KV 从 21GB 降到 3.7GB，才让 8GB 卡能跑。”

### 3.5 常见追问

- **“为什么不是固定分辨率？”** → Qwen2.5-VL 是动态分辨率，保留原图比例和细节；固定分辨率会拉伸/丢字。
- **“2M 怎么定的？”** → 在 8GB 显存和精度之间试出来的上限；再大就 OOM，再小掉字。
- **“小字看不清怎么办？”** → 切块/提高局部分辨率/接 OCR 先验；本项目没做，是未来工作。

## 4. 量化：bnb4 / NF4 / bf16

### 4.1 量化什么

- **权重**：bf16 → 4bit NF4；
- **激活**：保持 bf16；
- **KV cache**：单独实验（W3）。

### 4.2 核心结果（全量 624 张）

| 指标 | bf16 | bnb4 |
|---|---|---|
| exact F1 | 0.8451 | 0.8304 |
| normalized F1 | 0.9501 | 0.9330 |
| 延迟均值 | 19.6s | 7.1s |
| 延迟中位 | 17.1s | 6.0s |
| 峰值显存 | 7799MB | 3710MB |
| 权重显存（报告口径） | 6132MB | 2302MB |

**收益**：
- normalized −1.71pp；
- 中位延迟 ×2.85；
- 均值延迟 ×2.76；
- 峰值显存 −52%。

### 4.3 为什么 bnb4 更快

1. 加载后权重显存 6132MB → 2302MB，内存带宽压力大降；
2. 4bit 反量化到 bf16 有开销，但矩阵乘是带宽受限，省下的带宽 > 反量化开销；
3. bf16 峰值 7799MB 已接近 8GB，容易触发共享内存/碎片；bnb4 3710MB 留足余量。

**不能说**：“量化一定快。” 在算力受限/大 batch/反量化占比高时可能不变快。本项目的结论有明确条件：这个模型、这张卡、这个 batch。

### 4.4 NF4 vs INT4

- NF4：按正态分布分位点取 16 个值，更适合权重；
- INT4：均匀量化，对 outlier 不友好；
- 本项目：NF4 + double quant + bf16 compute。

### 4.5 精度代价怎么讲

> “同一批 624 张图、同一 prompt、同一台机器：normalized 从 0.9501 掉到 0.9330，1.7 个点；换 2.85 倍中位速度和一半峰值显存。这个 trade-off 在边缘场景是划算的。”

### 4.6 常见追问

- **“为什么掉 1.7 个点？”** → 4bit 权重误差 + 反量化；在可接受范围。
- **“能不能不掉点？”** → 8bit/NF4 + LoRA 微调/QAT；本项目没做。
- **“为什么权重显存 6132MB 而磁盘 7.5GB？”** → 磁盘是 bf16 两分片合计；6132MB 是加载后的显存口径（报告测量），不是磁盘大小。

## 5. 推理系统：prefill/decode、KV、批处理、并发

### 5.1 两个阶段

- **prefill**：整段输入（文本+视觉 token）并行过一遍，算 KV cache；计算密集；
- **decode**：逐 token 生成，每步只算一个新 token，但要读全部 KV；内存带宽密集。

单图约 4~7 秒（bnb4，取决于图像大小；报告全量均值 7.1s，现场 042 约 4.5s），大部分时间在 prefill（视觉 token 多）和 decode（生成 JSON）。

### 5.2 批处理

| batch | 吞吐（张/秒） | 单张延迟 | 峰值显存 |
|---|---|---|---|
| 1 | 0.178 | 5.63s | 3670MB |
| 2 | 0.228 | — | 4968MB |
| 4 | 0.247 | 4.04s | 7591MB |

**解读**：
- 吞吐 0.178→0.247，1.39×，不是线性 4×；
- 单卡算力/带宽固定，decode 仍逐 token；
- batch 4 峰值 7591MB，接近 8GB 上限。

**静态 vs 连续批处理**：
- 静态：凑齐一批一起跑，短请求等长请求；
- 连续（continuous batching）：完成即换入新请求，吞吐更高；
- 本项目是静态批处理；vLLM 连续批处理是未来工作（Windows 装不了 vLLM）。

### 5.3 KV 量化

- int8：基本无损；
- int4：直接崩；
- 原因：KV 里有 outlier，4bit 表示范围不够，attention 分数失真；
- 改进：group-wise/outlier 分离/KIVI 风格；本项目没做。

### 5.4 prefix cache 为什么 R≈0

- prefix cache 复用相同前缀的 KV；
- 每张图不同，system prompt 很短；
- 可复用 token 占比低 → 收益接近 0；
- **负结果的价值**：避免把工程预算花在无效优化上。

### 5.5 并发与 QPS

| 并发 | QPS | P95 |
|---|---|---|
| 1 | 0.18 | 5.9s |
| 2 | 0.22 | 9.1s |
| 4 | 0.22 | 18s |

**解读**：
- 单卡推理被锁串行化，QPS 上限约 0.22（≈1/4.5s）；
- 并发增加只排队，延迟线性涨；
- Little's law：$L=\lambda W$；QPS 不变、并发翻倍 → 延迟翻倍。

**讲解要点**：
> “并发只涨延迟、不涨吞吐，说明系统已经打满单卡。要提吞吐只能多卡/连续批处理/更小模型，不能靠加线程。”

### 5.6 为什么用锁

- 8GB 卡，两个请求同时 forward 显存叠加 → OOM；
- FastAPI 的 sync endpoint 跑在线程池，锁让请求排队而不是阻塞事件循环；
- 这是“单卡单模型”的正确做法；多卡才考虑并行。

### 5.7 常见追问

- **“为什么不用 vLLM？”** → Windows + Blackwell（sm_120）没有可用 wheel；bnb4 是当前可落地方案。
- **“为什么不用 TensorRT？”** → 多模态动态 shape/视觉 token 复杂，工程成本高；本项目先做可用的基线。
- **“batch 4 为什么不再大？”** → 7591MB 已接近 8GB；再大 OOM。
- **“QPS 0.22 能上线吗？”** → 小流量原型可以；生产要优化/多卡。

## 6. 服务化：FastAPI、lifespan、单例

- **lifespan**：启动加载模型，关闭释放；避免每请求重载；
- **全局单例**：`_model` / `_processor` 只加载一次；
- **Pydantic**：请求/响应 schema 校验，自动 OpenAPI 文档；
- **`/health`**：返回 `model_loaded`，演示前确认；
- **`/extract`**：上传图片，返回四字段 JSON。

**讲解点**：
> “模型服务化是 MLSys 的最后一公里：把离线推理包成 API，才能讲并发、吞吐、SLO。”

## 7. 精度定位与误差分析

### 7.1 SROIE 结果

- exact F1 0.8304；
- normalized F1 0.9330；
- 624 张（原始 626，剔除 2 个计时异常样本）。

### 7.2 和 SOTA 的关系

- SROIE 官方 SOTA 约 0.95；
- 但那是**训练过 + OCR 先验**的序列标注；
- 本项目是**零样本 3B 4bit 生成式**；
- 口径不同，不能直接比。

**讲解要点**：
> “0.933 normalized 不能和 0.95 直接比。它是零样本、4bit、生成式；要公平比，需要同训练数据/同 OCR 条件。我没做那个对照，所以只说‘在这个约束下可用’，不说 SOTA。”

### 7.3 误差分布（bnb4）

| 类别 | 占比 | 含义 |
|---|---|---|
| correct | 82.97% | 四字段严格正确 |
| noise | 10.26% | 大小写/标点/OCR 噪声，语义正确 |
| wrong | 6.61% | 语义错误 |
| hallucination | 0.08% | 图中不存在的内容 |
| missing | 0.08% | 空字段 |

**解读**：
- 大部分误差是 noise（归一化后算对），所以 normalized 0.9330 远高于 exact 0.8304；
- 语义错误 6.61% 是真正要改的；
- 幻觉/缺失各 0.08%，绝对数量很小（624×4 字段里约 2 个），不要过度解读。

### 7.4 跨域 XFUND

- 50 张中文表单，零样本；
- 字段级 normalized F1 **0.4072**（P 0.4257 / R 0.3903）；
- 说明模型懂通用“字段→值”抽取，不是背 SROIE 四字段；
- 但 0.4072 远不可用，跨语言/跨版式是明确局限。

### 7.5 常见追问

- **“624 不是 626？”** → 原始 626，剔除 2 个计时异常样本；这 2 张预测本来正确，不影响精度结论。
- **“幻觉只有 0.08% 可信吗？”** → 严格口径下的低比例，但绝对数量小；小样本比例不稳定。
- **“图像旋转/模糊怎么办？”** → 当前没做鲁棒性增强；Qwen2.5-VL 有一定鲁棒性，但没系统测。
- **“为什么地址字段最长最难？”** → 长文本、换行、标点、OCR 噪声；exact 最吃亏，normalized 好很多。

## 8. 高频问答（25 题）

> 模板：结论 → 证据 → 边界。

### Q1. 你这个项目只是调用了一个现成模型，贡献在哪？

**结论**：贡献在边缘部署的系统测量与优化，不是训练新模型。
**证据**：量化 Pareto、视觉 token 约束（21GB→3.7GB）、批处理/并发压测、服务化。
**边界**：模型是官方权重；我没有微调，这是事实。

### Q2. 为什么零样本能到 0.93？

**结论**：Qwen2.5-VL 本身有强文档理解能力；SROIE 四字段是常见版式。
**证据**：normalized 0.9330；exact 0.8304。
**边界**：仅在 SROIE；XFUND 跨域只有 0.4072。

### Q3. SROIE SOTA 0.95，你 0.93 是不是不如？

**结论**：口径不同，不能直接比。
**证据**：SOTA 是训练+OCR 先验的序列标注；我是零样本 3B 4bit 生成式。
**边界**：公平对比需要同训练数据/同 OCR 条件；我没做。

### Q4. 量化为什么能加速？

**结论**：加载后权重显存 6.1GB→2.3GB（报告口径），内存带宽压力大降；反量化开销小于省下的带宽。
**证据**：中位 17.1s→6.0s（×2.85）；峰值 −52%。
**边界**：不是所有场景都快；算力受限/大 batch 可能不变快。

### Q5. 量化掉了多少精度？

**结论**：normalized −1.71pp，exact −1.47pp。
**证据**：0.9501→0.9330；0.8451→0.8304。
**边界**：624 张全量；2 张计时异常样本剔除，不影响精度结论。

### Q6. 为什么是 624 不是 626？

**结论**：原始 626，剔除 2 个计时异常样本；这 2 张预测本来正确。
**证据**：数据清洗记录；精度结论在全量一致。
**边界**：不是挑好数据；可提供清单。

### Q7. 视觉 token 是什么？为什么要限制？

**结论**：图像 patch 进 LLM 后的 token；越多越吃显存/KV。
**证据**：84 张 >1 万 token，最大 16307；无约束 15.97GB OOM；限制后 ≤2669，总量 −51%。
**边界**：限制损失小字；是质量-成本权衡。

### Q8. 为什么 KV cache 从 21GB 降到 3.7GB？

**结论**：视觉 token 总量降约一半，KV 随 token 线性降；加 4bit 权重。
**证据**：visual_tokens_kv.md。
**边界**：具体数字依赖 batch/序列长度；现场说“约”更稳。

### Q9. KV int8 无损、int4 崩，为什么？

**结论**：int8 误差小；int4 对 KV outlier 太粗，attention 失真。
**证据**：w3_kvquant.md。
**边界**：int4 可用 group-wise/outlier 分离改进；我没做。

### Q10. prefix cache 为什么没收益？

**结论**：每张图不同，system prompt 短，可复用前缀少。
**证据**：R≈0。
**边界**：负结果；说明这个场景不该投 prefix cache。

### Q11. 批处理吞吐为什么只涨一点？

**结论**：单卡算力/带宽瓶颈；batch 4 显存接近上限。
**证据**：0.178→0.247（1.39×）；延迟 5.63→4.04s；峰值 7591MB。
**边界**：连续批处理可能更好，但 Windows 没上 vLLM。

### Q12. 并发为什么 QPS 不涨？

**结论**：单卡串行，QPS 打满；并发只排队。
**证据**：0.18/0.22/0.22；P95 5.9/9.1/18s。
**边界**：要提吞吐需多卡/连续批处理/更小模型。

### Q13. 为什么用锁？不会阻塞吗？

**结论**：8GB 卡并发 forward 会 OOM；锁让请求排队，保护显存。
**证据**：两并发即 OOM；FastAPI sync endpoint 在线程池，锁不阻塞事件循环。
**边界**：吞吐上限低；这是单卡取舍。

### Q14. 为什么不用 vLLM？

**结论**：Windows + Blackwell（sm_120）没有可用 wheel；bnb4 是当前可落地方案。
**证据**：requirements 注释；vLLM/autoawq 装不上。
**边界**：Linux 上应换 vLLM 做连续批处理。

### Q15. XFUND 0.4072 是不是很差？

**结论**：跨语言、跨版式零样本，0.4072 说明有通用能力，但远不可用。
**证据**：P 0.4257 / R 0.3903；50 张中文表单。
**边界**：样本小，CI 宽；不能外推。

### Q16. 幻觉率 0.08% 可信吗？

**结论**：严格口径下的低比例，但绝对数量小。
**证据**：624×4 字段里约 2 个；error_analysis_bnb4.md。
**边界**：小样本比例不稳定；不要拿它说“几乎不幻觉”。

### Q17. 图像旋转/模糊怎么办？

**结论**：当前没做鲁棒性增强；Qwen2.5-VL 有一定鲁棒性，但没系统测。
**证据**：SROIE 原图；未做旋转/模糊 benchmark。
**边界**：明确未来工作；不要编数字。

### Q18. 为什么选 3B 不选 7B？

**结论**：8GB 边缘设备；3B 4bit 峰值 3.7GB，余量足。
**证据**：bnb4 权重 2302MB、峰值 3710MB。
**边界**：7B 精度可能更高；我没做 7B 对照。

### Q19. 这个项目能上线吗？

**结论**：能作为单机小流量原型，离生产还有距离。
**证据**：FastAPI + 健康检查 + 压测；QPS 0.22。
**边界**：缺鉴权、限流、监控、多卡/连续批处理、失败重试。

### Q20. 你个人做了什么？

**结论**：数据/评估/量化/压测/服务化全链路。
**证据**：报告、脚本、FastAPI、Pareto 图。
**边界**：模型权重是官方的；我没有声称训练了 VLM。

### Q21. 为什么不用 OCR + 规则/分类？

**结论**：端到端 VLM 少了 OCR 误差传播和版式规则维护；零样本就能抽。
**证据**：normalized 0.9330；无需训练 OCR。
**边界**：OCR + 规则在固定版式上可能更稳/更便宜；我没做对照。

### Q22. 为什么不用 LayoutLM/Donut 等文档模型？

**结论**：Qwen2.5-VL 是通用多模态，零样本即可；LayoutLM 类通常要训练。
**证据**：零样本 0.9330；未训练。
**边界**：专用文档模型在 SROIE 上可能更高；口径不同。

### Q23. 为什么不做微调？

**结论**：项目目标是边缘部署与系统测量；零样本已可用。
**证据**：0.9330 normalized；量化/压测是重点。
**边界**：微调可能再涨点，但会引入训练数据/过拟合/部署复杂度；未来工作。

### Q24. 你的系统和 PaddleOCR 比怎么样？

**结论**：不是同一层：PaddleOCR 做检测/识别，我做端到端字段抽取。
**证据**：输入图片直接输出四字段 JSON；不需要 OCR 中间结果。
**边界**：PaddleOCR 可作为 OCR 先验提升小字；我没集成。

### Q25. 如果给你更多时间，先做什么？

**结论**：先做连续批处理/多卡吞吐，再做微调/OCR 先验提升精度。
**证据**：当前瓶颈是 QPS 0.22 和跨域 0.4072。
**边界**：不是盲目换更大模型；先把系统吞吐和跨域补齐。

## 13. 与项目一的交叉问答

### Q26. 两个项目有什么共同点？

**结论**：都是“非结构化 → 结构化”，都强调可量化评估。
**证据**：文本→JSON；图片→JSON；都用 P/R/F1 + 误差分析。
**边界**：一个训练、一个部署；方法论互补。

### Q27. 哪个更难？

**结论**：难在不同维度。
**证据**：SciTriple 难在数据和评估；VLM 难在系统约束（8GB、视觉 token、并发）。
**边界**：不要比较“谁更牛”，比较“难在哪”。

### Q28. 你最大的技术贡献？

**结论**：把模型能力落到可复现的评估与部署。
**证据**：四层对照 + CI + 多 seed；量化 Pareto + 压测。
**边界**：不是提出新算法，是工程与实验方法。

### Q29. 最大的不足？

**结论**：标签质量与绝对精度。
**证据**：SciTriple 测试标签是模型标注；VLM 跨域 0.4072。
**边界**：改进方向明确：人工金标准、span 约束解码、微调/OCR 先验。

### Q30. 评审说“都是现成工具”，怎么回应？

**结论**：工具是现成的，但选型、对照、测量、边界是我的工作。
**证据**：为什么 1.5B/3B、为什么 QLoRA/bnb4、为什么 2M 像素；每个选择都有数据。
**边界**：不声称发明 LoRA/量化；声称能正确使用并量化代价。

### Q31. 怎么保证可复现？

**结论**：固定 seed/数据切分/解码/配置与报告。
**证据**：config、3 seed、bootstrap、离线模型缓存。
**边界**：GPU 非确定性/驱动差异仍可能带来小幅波动；没做容器化。

### Q32. 怎么保证代码质量？

**结论**：模块化 + 测试 + 自检。
**证据**：VLM 48 tests；FastAPI Pydantic；SciTriple 75 tests + 7 维自检。
**边界**：没有 CI/CD；测试以核心逻辑为主。

### Q33. 为什么选浙大软院？

**结论**：想把工程能力推进到系统/研究结合。
**证据**：两个项目分别碰训练与部署；想研究结构化抽取的评估与高效推理。
**边界**：说具体方向，不要背校训。

### Q34. 本科背景不占优，怎么证明能跟上？

**结论**：用可验证的产出证明。
**证据**：两个完整项目、报告、测试、复现；408/数学备考。
**边界**：不回避背景，强调自驱和工程闭环。

### Q35. 读过什么论文？

**结论**：LoRA、QLoRA、NF4、Qwen2.5-VL、SROIE/XFUND 相关工作。
**证据**：能讲 LoRA 公式、NF4、视觉 token、KV cache。
**边界**：不要编没读过的论文；被追问细节就承认“只读了摘要/实验部分”。
